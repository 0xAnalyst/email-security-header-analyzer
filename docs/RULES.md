## Details

### ESHA-001: DMARC passed

The From domain was authenticated by SPF or DKIM aligned with it.

### ESHA-002: DMARC failed

Neither SPF nor DKIM authenticated the domain shown in From, so the sender may be spoofing it.

**What to do:** Treat the From address as unverified. Check the alignment table to see which domain really sent it.

### ESHA-003: Sender's DMARC policy is p=none

The domain owner only monitors spoofing and does not ask receivers to block it.

**What to do:** If this is your domain, move to p=quarantine or p=reject once reports show legitimate mail aligns.

### ESHA-004: No DMARC verdict

No DMARC result was recorded; the sender may not publish a DMARC policy.

**What to do:** Missing DMARC makes the From domain easy to spoof. Weigh the other findings more heavily.

### ESHA-005: SPF passed and aligned

The sending server is authorised for the envelope domain, which matches From.

### ESHA-006: SPF passed for a different domain

SPF passed, but for an envelope domain unrelated to the From domain. Normal for mail services when DMARC passes; a common spoofing trick when it doesn't.

**What to do:** Rely on DMARC, not SPF alone. An SPF pass only proves the server may send for the envelope domain.

### ESHA-007: SPF failed

The sending server is not authorised to send for the envelope domain.

**What to do:** Treat the message as spoofed unless it was forwarded (forwarding breaks SPF).

### ESHA-008: SPF soft-failed

The domain owner says the server is probably not authorised.

### ESHA-009: SPF error

The SPF record could not be evaluated (permerror or temperror).

### ESHA-010: DKIM signature valid and aligned

A valid DKIM signature from the From domain proves the message came from that domain unmodified.

### ESHA-011: DKIM signed by a different domain

The signature is valid but belongs to another domain, often a mail service. That proves who relayed the message, not who the From address claims.

**What to do:** Check whether the signing domain is a service the sender is known to use.

### ESHA-012: DKIM failed

A DKIM signature was present but did not verify; the message may have been altered in transit.

**What to do:** Mailing lists and forwarding can break signatures. Without that explanation, assume tampering.

### ESHA-013: Message is not DKIM-signed

No DKIM signature, so the content and From address are not cryptographically protected.

### ESHA-014: DKIM signature present but no verification result

The headers contain a DKIM signature but no receiving server's verification result.

### ESHA-015: Microsoft composite authentication failed

Microsoft 365 combined SPF, DKIM, DMARC and its own signals and concluded the sender is not authentic.

**What to do:** Microsoft's verdict is usually reliable. Check reason= codes 000 (explicit DMARC fail) and 001 (implicit).

### ESHA-016: ARC chain is broken

A forwarding service's authentication seal failed validation, so earlier results can't be trusted.

### ESHA-017: Conflicting SPF results

Authentication-Results and Received-SPF disagree, which can mean an inserted or stale header.

### ESHA-018: Authentication-Results from an unexpected server

An Authentication-Results header claims a pass but was added by a server not in the relay path. Attackers insert fake results to fool analysts and weak filters.

**What to do:** Only trust the top-most Authentication-Results added by your own mail system.

### ESHA-020: DKIM signature does not cover From

The signature's h= list omits From, so the visible sender can be changed without breaking it. RFC 6376 requires From to be signed.

**What to do:** Don't treat this signature as proof of the sender. If it is your domain, fix the signer configuration.

### ESHA-021: DKIM signature only covers part of the body (l= tag)

With l=, anyone can append content (links, forms) after the signed part and the signature still passes.

**What to do:** Read the message as if any content after the first part is unauthenticated. Signers should not use l=.

### ESHA-022: DKIM signature covers few headers

Important headers such as Subject are not signed and could have been changed after signing.

### ESHA-023: BIMI brand logo

The receiving server verified BIMI and may show the brand's logo next to the message.

### ESHA-024: BIMI header on unauthenticated mail

BIMI-Location or BIMI-Indicator is present but DMARC did not pass. Receivers only add these after DMARC passes, so the sender probably inserted them to borrow a brand logo.

**What to do:** Ignore any logo shown with this message.

### ESHA-101: Display name contains a different email address

The display name shows one address while the message comes from another.

**What to do:** Look at the real address in angle brackets, not the name. Confirm the request through a known channel (phone number or address you already have), not by replying or using contact details in the message.

### ESHA-102: Look-alike domain imitating a brand

The sender's domain imitates a well-known brand with typos, look-alike characters or the brand name embedded in another domain.

**What to do:** Block the domain and search mail logs for other messages from it.

### ESHA-103: Display name claims to be a brand

The display name names a brand, but the address belongs to an unrelated domain.

**What to do:** Confirm the request through a known channel (phone number or address you already have), not by replying or using contact details in the message.

### ESHA-104: Sender domain uses punycode (IDN)

Internationalised domains can contain characters that look like Latin letters.

### ESHA-105: Sent from a free webmail provider

Free webmail accounts are easy to create; be wary if the message claims to be from a company.

### ESHA-106: From header missing or unparseable

Legitimate mail always has a parseable From address.

### ESHA-107: Reply-To imitates the sender's domain

Replies go to a domain that imitates the sender's own, the pattern of invoice and payroll fraud (BEC).

**What to do:** Do not reply. Confirm the request through a known channel (phone number or address you already have), not by replying or using contact details in the message. Block the look-alike domain.

### ESHA-108: Reply-To differs from From

Replies go to a different organisation than the sender.

**What to do:** Before replying, check that the Reply-To address belongs to the person you expect.

### ESHA-109: Return-Path differs from From

Bounces go to another domain, which is normal for mailing services.

### ESHA-110: Sender header differs from From

The Sender header names another mailbox than From.

### ESHA-120: Sent through an email service provider

The message was sent through a known email service provider (ESP). Envelope, DKIM and Message-ID domains belonging to that ESP are expected and explained in the other findings.

### ESHA-201: No Received headers

There is no relay path. These may not be the original headers, or the message was injected locally.

**What to do:** Get the full original headers (Show original / View source) before drawing conclusions.

### ESHA-202: Sending server has no reverse DNS

Legitimate mail servers almost always have a reverse DNS name.

### ESHA-203: Sent from a residential or dynamic IP

The sending address looks like a home or dynamic connection, typical of compromised machines and spam.

### ESHA-204: Sending server greeted with a bare IP address

Real mail servers normally announce their hostname.

### ESHA-205: Clock skew between relays

A hop is timestamped before the previous one, usually a mis-set server clock.

### ESHA-206: Significant delivery delay

At least one hop took an hour or more.

### ESHA-207: Timestamps without a time zone

Some relay timestamps have no time zone; UTC was assumed.

### ESHA-208: Encrypted in transit

Every relay from a public IP used TLS.

### ESHA-209: Some relays show no sign of TLS

Some public hops don't record TLS. Not proof of plain text, since not all servers log it.

### ESHA-301: Message-ID missing

Legitimate mail servers almost always add a Message-ID.

### ESHA-302: Message-ID domain differs from From

The Message-ID was generated by another domain's system.

### ESHA-303: Bulk or scripted mailer

The X-Mailer or User-Agent is a bulk-mail tool or script library often used by spammers.

### ESHA-304: Urgent or account-related wording in subject

Urgency and account warnings are classic social-engineering pressure.

### ESHA-305: Date header missing

Every legitimate message has a Date.

### ESHA-306: Date header could not be parsed

The Date header is malformed.

### ESHA-307: Date header is later than the first relay

The message claims to be written after it was relayed, so the Date may be forged.

### ESHA-308: Message was written long before it was sent

A week or more passed between the Date and the first relay.

### ESHA-309: No To recipients

Recipients were hidden (Bcc or undisclosed), common in mass phishing.

### ESHA-320: Bulk mail without List-Unsubscribe

The message is marked as bulk or list mail but has no List-Unsubscribe header. Gmail and Yahoo require one from bulk senders, so legitimate marketing almost always has it.

**What to do:** If you don't recognise the sender, report it as spam rather than looking for an unsubscribe link.

### ESHA-321: List-Unsubscribe without one-click

The List-Unsubscribe header has a web link but no List-Unsubscribe-Post header (RFC 8058), so mail clients can't offer a safe one-click unsubscribe.

### ESHA-322: Subject looks like a reply, but the message isn't part of a thread

"RE:" without In-Reply-To or References headers makes a first contact look like an ongoing conversation.

**What to do:** Check your sent mail: did you ever write to this sender about this subject?

### ESHA-323: Thread headers with a new subject

In-Reply-To or References point to an earlier conversation, but the subject isn't a reply or forward. Normal for many notification systems; in a personal thread it can be a sign of hijacking.

### ESHA-324: Reply from a look-alike of a thread participant's domain

The message continues an existing thread but comes from a domain that imitates one of the participants' domains, the pattern of thread hijacking after a mailbox compromise.

**What to do:** Contact the real participant through a known channel. Check whether their mailbox was compromised.

### ESHA-401: Disguised attachment

The attachment's real type is hidden by a double extension or doesn't match its name.

**What to do:** Do not open the attachment. Report the message and submit the file to your sandbox or EDR team for analysis.

### ESHA-402: Risky attachment

The attachment type can run code or open a page (HTML, scripts, executables, shortcuts, disk images, macro documents).

**What to do:** Do not open the attachment. Report the message and submit the file to your sandbox or EDR team for analysis.

### ESHA-403: Archive attachment

Archives can hide their contents from some scanners.

### ESHA-404: Message contains a login or data form

Legitimate services do not ask you to enter credentials inside an email or attachment.

**What to do:** Do not enter anything. Report the message and reset the password if anything was submitted.

### ESHA-405: Link to a look-alike domain

A link points to a domain imitating a well-known brand.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-406: Link text does not match where it goes

The visible link text shows one domain but the link goes to another.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-407: Script link in message

A javascript: or vbscript: link runs code when clicked.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-408: Link opens an embedded page

A data: link opens a page stored inside the link itself, bypassing URL filters.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-409: Link to a file share

file:// or UNC links can leak Windows credentials (NTLM hashes) when opened.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-410: Link points to a raw IP address

Legitimate services link to named domains, not raw IP addresses.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-411: Link uses a punycode domain

Internationalised domains can imitate familiar names.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-412: Link hides its real host after an @

In user@host URLs the part before @ is ignored, so the real destination is hidden.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-413: Link to free hosting often used for phishing

Free hosting, form and file-sharing services are popular for short-lived phishing pages.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-414: Shortened link hides its destination

URL shorteners hide the real destination.

### ESHA-415: Link to a look-alike of the sender's domain

A link goes to a domain imitating the sender's own organisation.

**What to do:** Do not open the link. Report the message, and block the domain at the mail and web gateway if it is malicious.

### ESHA-416: No links point to the sender's own domain

All links go to other organisations. Common for marketing and redirect services.

### ESHA-420: HTML smuggling in attachment

An HTML or SVG attachment contains code that builds a file in the browser (atob, Blob, msSaveOrOpenBlob, large base64 data). This delivers malware past mail gateways.

**What to do:** Do not open the attachment. Report the message and submit the file to your sandbox or EDR team for analysis. If it was opened, check the Downloads folder and EDR telemetry on that machine.

### ESHA-421: Password-protected archive

The archive is encrypted, so mail gateways and antivirus can't inspect it. The password is usually in the message body.

**What to do:** Do not open the attachment. Report the message and submit the file to your sandbox or EDR team for analysis.

### ESHA-422: Archive inside an archive

Nesting archives is a common way to slip past scanners that only unpack one level.

**What to do:** Do not open the attachment. Report the message and submit the file to your sandbox or EDR team for analysis.

### ESHA-423: Risky file inside archive or disk image

An archive or disk image contains shortcuts, scripts or programs. ISO, IMG and VHD files also bypass Windows' Mark-of-the-Web warnings.

**What to do:** Do not open the attachment. Report the message and submit the file to your sandbox or EDR team for analysis.

### ESHA-424: Calendar invite from an outside organiser

The invite's organiser is not the sender's domain. Calendar clients may add invites automatically, so phishers use them to get links into calendars without the message being opened.

**What to do:** Remove the event from the calendar and report it. Don't join or open links from it.

### ESHA-425: Links in a calendar invite

The invite description or location contains links. They are listed with the other links.

### ESHA-426: Message is mostly an image

There is almost no text, just images. Phishers use image-only mail and QR codes to hide links from filters.

**What to do:** Don't scan QR codes or follow instructions in an image from an unverified sender.

### ESHA-427: Message asks you to scan a QR code

QR-code phishing (quishing) moves the link to a phone, outside company protection. ESHA does not decode QR codes.

**What to do:** Don't scan it. If you did and entered credentials, reset the password and revoke sessions.
